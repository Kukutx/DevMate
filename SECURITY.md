# Security Policy

DevMate 4 is a personal local runtime with one owner and no other identity. It has filesystem, Git, native agent, command, browser, Godot, reverse-engineering and Obsidian capabilities. Code execution is performed under the operating-system account that runs the selected provider or host.

## Connections and identity

The runtime binds to `127.0.0.1` on two ports. The control port is the owner's local surface: CLI, editor hosts, the localhost workbench and MCP clients on the same computer. The ingress port serves only MCP and OAuth and is the only port a tunnel or reverse proxy targets; the control port refuses any request that arrived through a proxy.

Local control uses the private instance owner token, which is never given to a browser. The localhost workbench is entered through a link that only the holder of that token can create (`devmate ui`, or the editor command): it works once and expires within a minute. The page of that link exchanges the code for a session that belongs to its browser tab. The session is not a cookie: a browser sends a cookie to every port of `127.0.0.1`, so every other local web service would receive it. The tab keeps the session to itself and presents it in a request header. Opening the control port in a browser without such a link shows a page that holds nothing and says how to get in.

One instance directory has exactly one runtime. Ownership is an operating-system endpoint (a named pipe on Windows, a Unix socket elsewhere) that exists only while the owning process lives, so concurrent starts from several editor windows, another editor and the CLI cannot produce two runtimes, and a record left by a crash is never mistaken for a running one.

MCP defaults to no authentication for both local and public ingress; OAuth is the owner's own sign-in on a public route. Public `auth.mode: none` does not prove caller identity, so that endpoint must remain private to the owner. On the control port a caller that presents no credentials is the local owner in either mode, so clients on the owner's own computer keep working when sign-in is enabled for the public address; a caller that presents a token is exactly who the token says, or is refused.

Every service and MCP call requires a verified identity; omitting it never grants owner authority. There are two: the owner, and the runtime's own check of its public route. With sign-in enabled that check presents a token it issued to itself, for a minute, to whatever answers at the public address; because that may be the wrong server, the token is not the owner's and is allowed one question only: which runtime is answering. It sees no project, no instructions and no other tool. The default `auth.mode: none` is the explicit single-owner trust model. Every request reaching `/mcp` receives owner authority. Keep such an endpoint private to the owner, including when a configured tunnel or HTTPS ingress is used.

A client keeps what connects it to DevMate in the account it is used with: the address with its key, the sign-in it was given, the tunnel that was chosen there. Whoever uses that account has the connection. A ChatGPT or Claude account the owner shares with another person gives that person's conversations the same DevMate tools, with the owner's authority and whatever the permission profile allows. DevMate sees one client and cannot tell the two people apart, and sign-in does not change this, because the sign-in is kept in the account as well. Connect DevMate in an account nobody else uses; where the account is shared, the profile and what is shared (read-only projects, no browser) are all that limits the other person.

A Cloudflare quick tunnel cannot ask for sign-in, because its host name is new with every start and nobody could sign in at it. Its host name is not a secret either: a name is looked up through DNS in the clear. The runtime therefore answers a quick tunnel only under `/mcp/<key>`, where the key is 24 random bytes made at every start and compared in constant time; the host name alone, `/mcp` and every other path answer "not found". The key travels only inside TLS and is never on the command line of the connector. It is a bearer secret in an address: whoever holds the whole address has owner authority, `devmate doctor` prints the address without it, a fault the runtime writes to its log names the path without it, and a client that stores the address stores the key. Cloudflare terminates TLS and sees the requests of a quick tunnel as it does of any tunnel it runs.

OpenAI's tunnel is spoken by the runtime itself unless the path of OpenAI's `tunnel-client` program is configured. The runtime then only makes outbound HTTPS requests to `api.openai.com`, authenticated with the tunnel's runtime key from the private credential store, and hands what it is given to its own ingress on the loopback address, with a secret of this start by which the ingress knows it (next paragraph). A call that arrives this way is the owner's connected client, in either `auth.mode`: OpenAI decides who may use the tunnel, and no sign-in page can be reached through one. Where OpenAI's `tunnel-client` program carries the tunnel instead, it cannot be told the secret: the ingress takes it by the loopback name it calls the port by, only where the tunnel is the only connection, and what it hands over is checked like a request from outside, so with `auth.mode: oauth` it needs a token. A call's headers are passed on to the endpoint except hop-by-hop fields and anything that claims where a request came from. The key is sent to that one host and appears in no log, status or report.

The tunnel can run beside a connection that has a public address (`devmate connect … --openai-tunnel <id>`): ChatGPT of the account the tunnel belongs to comes through the tunnel, every other client through the address. Both lead to the same ingress port, so the runtime has to know its own tunnel client there, and the loopback name it calls the port by is not enough: a reverse proxy that rewrites `Host` to that name (nginx does unless told otherwise) would turn every request from outside into the tunnel's. The tunnel client therefore says a secret with every call it hands over, 32 random bytes made at every start, compared in constant time, known to nothing outside the runtime process and never taken from a call's own headers; it counts only together with the loopback name. Beside another connection the runtime always speaks the tunnel itself: OpenAI's program cannot be told the secret. Three things follow, and they are the owner's to weigh:

- What is exposed is the sum of both. With a public address the computer is reachable from outside again, and whoever has that address (and signs in, where sign-in is on) has owner authority whether the tunnel runs or not. The tunnel's own property, that nothing listens for the outside, holds only where the tunnel is the only connection.
- Sign-in belongs to the address. What the runtime's own tunnel client hands over is served as the owner without it, in either `auth.mode`: no sign-in page can be reached through a tunnel, and OpenAI lets a tunnel be used by the account it belongs to and by nobody else. Who may use the tunnel is therefore decided in the OpenAI account, not in DevMate. `devmate doctor` says so in a line of its own (`security.tunnel`) beside "sign-in is required", and so does `devmate connect` when a sign-in is chosen with a tunnel beside it.
- The plain path `/mcp` on the ingress port is the tunnel's where the address has a key in it (a quick tunnel, a relay): from outside that path stays "not found".

A connected client that asks how DevMate is reached (`connection_status`) is told, in the guarded profile too, that a tunnel runs beside the address, whether it is connected, and which of the ways in its own request took (`via`). The tunnel ID, the address and what the connectors say are told to the owner at the computer, and to the owner's client where full access is on.

A relay of the owner's own (`devmate relay setup`) is a public server they control on which Caddy terminates TLS and forwards one path, `/mcp/<key>`, to a loopback port that this computer holds open with an OpenSSH remote forward. The key is 24 random bytes, kept in this instance's configuration and in the relay's site file, and stays the same so that the address does; every other path on the relay answers "not found". By default the relay also checks where a request comes from and answers only the published address ranges of ChatGPT and Claude and the address this computer last connected from; the ranges are fetched again every six hours and a list that cannot be read never replaces a good one. A relay cannot ask for sign-in, because the pages of a sign-in are not under the one path it forwards: the configuration refuses OAuth together with an address that ends in a key, so the key and the address list are what protects a relay, and the doctor says so. Setting a relay up runs a script as root on that server over the owner's SSH key login; it installs Caddy from the system's packages, or from Caddy's own package repository where the system has none or one too old for a certificate for an address, and never replaces a Caddy that was there before; no password is asked for or stored, and the first contact records the server's host key, which every later connection insists on. The relay sees the requests in the clear, as any TLS-terminating proxy does: it is the owner's machine.

Optional OAuth proves that a client of the public address is the owner. It uses the configured HTTPS issuer, resource-bound tokens, S256 PKCE, client metadata documents, one-use login and authorization codes, refresh rotation and grant revocation. A one-time code is created at the owner's computer (`devmate login-code`), and the owner can list and revoke every sign-in (`auth.grant.list`, `auth.grant.revoke`). Dynamic client registration and copied static tokens are not supported.

A signing-in client's metadata document is fetched from a public address only: the host name is looked up here, every address it has must be public, and the request is pinned to the address that was checked. Where the computer is set to use a proxy (the `HTTPS_PROXY` variable, or the Windows system proxy), the runtime's requests to the outside go through it, and it is the proxy that looks the name up and connects: the request can then not be pinned to a checked address. The name itself must be a public one (no address, no single-label or local-network name), and it is still looked up on this computer, for a second and a half at most: a name that answers here with an address of this computer or of a local network is refused before the proxy is asked. A name this computer cannot look up, or only to the made-up addresses of a proxy tool, is left to the proxy; a name that answers differently to this computer and to the proxy is not caught by this. In every case the certificate is checked, no redirect is followed and only a small JSON document with status 200 is taken. Requests to this computer itself never go through a proxy. A proxy address is shown without the credentials in it.

A configured public Host exposes the MCP and OAuth routes only. Local control, owner recovery, settings, host binding and the localhost UI remain private local surfaces. A local owner token does not authorize a public OAuth request. Tunnel process readiness is not proof of a working remote connection.

## Project access and trusted execution

What an editor window shares is the owner's setting (`devMate.shareFolders`). By default a trusted local folder opened in VS Code is shared with connected clients, read and write, and the window says so once with a way to change it; the owner can make any folder read only or take it out at any time, and a folder taken out stays out. The setting can instead ask first, share read only, or share nothing. Folders of an untrusted workspace are never shared. Each editor window acts only on its own selected project.

Because the default shares what is opened, a public address without sign-in gives whoever has it write access to every folder open in an editor that runs the extension. Use sign-in, or `ask`/`never`, when that is not intended.

What is shared, and how far, is decided by the owner at their computer: in an editor, on the command line (`devmate project add`), or in the local workbench. A client reaching DevMate through MCP, whether a model, a script or a workbench embedded in a chat app, cannot share a folder, cannot make a read-only project writable, cannot lift the credential-file protection and cannot change how a capability engine is set up. It can narrow all of these: make a project read only, take a folder out, switch an engine off. A folder taken out stays out, also for the folder above it and the folders inside it, until its owner shares it again. The two sharing settings of the VS Code extension are machine-scoped, so a repository's workspace settings cannot change them.

How far this holds depends on one thing. **A client with write access to any project can run commands, and commands run as the owner's operating-system account.** From there it can read any file the owner can read, including the owner token of this DevMate. So with at least one writable project, the limits on the *other* folders (read only, protected files, taken out) keep a well-behaved model from wandering; they are not a wall against a hostile one. With only read-only projects shared there are no commands and no agents, and the limits above are a boundary: that is the setting to use for a client you do not fully trust.

Decisions an agent waits for (approvals, questions) are the person's, and they are answered at the computer: in the editor, or in the local workbench. No client connected through MCP can answer them, whatever it declares about itself, because the caller may be the very model that started the agent. An embedded workbench shows what is waiting and says where to answer it.

What a coding agent does is spent on the owner's account with the agent's provider. In the default setting (`devmate delegation ask`) a task that reaches an agent through a connected client is therefore held where it is taken in, and an approval of the kind `delegation` waits for the owner: run this one task; run it and do not ask again for this agent for as long as it stays connected, which covers its later tasks and what a client adds to a task that runs, the owner's own among them; or do not run it. The owner is shown what they agree to: the task as the provider will be given it (for what an agent passes on, with the line that says which agent it is from), of a very long one its first 20,000 characters with how much more there is and where it is read, the model it would run with, and a session of the provider that would be taken up again; the model and that session are the client's to choose where it wrote the agent down. Names a client chooses (of an agent, of a project, a model, a session to take up) stand in quotes, on one line and cut short, in the question and in each line under it; no quotation mark of their own ends those quotes (each is shown as an apostrophe) and no character of theirs turns the line around, so everything outside the quotes is DevMate's own. Where the client chose the model or the session, that is said beside it.

There are three ways for a client's words into a turn. A task of its own goes through one place, where it is taken in for an agent, whichever operation brought it: `agents.delegate`, `agents.start` with a prompt, `agents.send`, `message.send`, a task with an assignee, a turn that is tried again, and what an agent writes to another agent. That is the one that is held. Text put into a task that already runs (`agents.steer`) is the second: a connected client does that only for an agent whose later tasks the owner allowed. The third exists in the full access profile only: there a connected client may answer what an agent asks, and its answer to a question is text of its own in the task that runs. It is not refused, because handing a client the answers is what the owner chose with that profile, and it is not subject to `delegation off` either; in the guarded profile no client answers. What an agent passes on counts as its task's: on a client's task, or one a client steered or answered a question of, it is the client's and is asked about; between tasks it counts as the last task's, and before the first as whoever started the agent. A task that is held starts nothing: no process, no place among the sessions, no copy of the project beyond the one a client asked for with `isolate` (which is removed again when the task is not allowed), and no turn counted against its workflow until it is allowed; a connected client cannot start an agent's process on its own either (`agents.start` only writes the agent down, with the status `unstarted`, and `agents.resume` is refused). The agent runs whatever else it has meanwhile. At most twenty tasks wait for the owner at once; one beyond that is refused before anything is made for it, with how many the owner has before them, and where the owner chooses to be asked again, the tasks that had been let through and had not begun wait for their answer up to that number, oldest first, and the rest is ended and says so. A yes is refused, and the question stays, for as long as the task could not begin (no session is free, its workflow is paused or out of turns, its project is read only); where the owner chose not to be asked, such a task waits, says what for, and is let through when that is out of the way. A question ends with what it waited in: the agent being stopped, its workflow completed, its project taken out of sharing, its work in a copy applied or discarded. An agent that was only written down and whose tasks all ended before one began (refused, taken back, or lost to a restart) is closed, and a workflow that was made for such tasks alone is completed. A client's message is in an agent's inbox only where the record of its handing over says it was given, so a held or refused one is not, also after that record has been removed with age; and a client's message is named as a client's there, not as "You".

The answer is given at the computer alone, in either profile: `approval.resolve` refuses it to a connected client, with full access too, and choosing full access does not grant what waits, because the client that asked would be the one answering. The browser extension keeps a client out of the workbench tab, where the answer is given (below). What the owner hands to an agent at the computer is not held. The owner can choose `allow` (nothing is held, and what waits is let through) or `off` (a connected client is refused before anything is made for its task, what waited or was queued for it ends, and it is not offered `agents.delegate`, `agents.start`, `agents.send`, `agents.steer`, `agents.resume` or `message.send`); choosing `ask` again has every agent asked about again, and every task of a client that was let through and has not begun. `delegation.update` is a local operation in either profile, and the choice is stored with the instance. What waits when the runtime stops is not carried over. An agent's "later tasks" is said of the session it has at that moment and ends with it: when the agent is stopped, when its process goes or cannot be started, when the runtime restarts. A session that is started afterwards, by a task that is allowed or by the owner's own hand, begins without it. A yes for a task that cannot begin (no session is free for its agent, its workflow has no turns left) is refused with that and leaves the question standing; with `allow`, such tasks are let through as sessions end.

A release that knows nothing of this must not run on state where it was chosen: a runtime of 4.0.5 would run a client's tasks unasked. The state carries a format number for that. A release before this one refuses an instance this one has used, naming both, so an entry that was not updated cannot start such a runtime; it can still join a runtime of this release that is running.

This keeps a model's own initiative, and another person's conversation on an account that is shared, from spending what the owner did not choose to spend. It is not a wall against a client that means to: with a writable project a client runs commands, and the command line of an installed agent (`codex`, `claude`) is a command like any other, on the same account. The paragraph on write access above holds here as well. Two things lie outside it by their nature: what a provider's own sessions say to each other where the owner switched that on (`nativePeerMessaging` for Claude Code, off by default) does not pass through DevMate; and a question that is never answered waits until the task is taken back, the agent is stopped or the runtime restarts.

### The full access profile

The two paragraphs above describe the default profile, *guarded*. The owner can replace it with *full access* (`devmate access full`, or the editor command). `access.update` is a local operation: no MCP path reaches it in either profile. The choice is stored with the instance, applies at once, and is reported by `devmate doctor`.

With full access, the owner's connected client may do what otherwise needs the owner's computer: share a folder (`project.create`), widen a project, lift the credential-file protection, configure capability engines, answer approvals and questions, and read what says why something does not work (`runtime.doctor`, `runtime.metrics`, the names of stored credentials, the full connection status). Credential-like files are no longer withheld in the file tools and the project overview, whatever a project's own setting says. What a delegated agent asks permission for is granted by the runtime at once, preferring the option that grants it one time; every such grant is kept as an approval record marked automatic. A question an agent asks, and a permission request that offers no granting option, still wait for an answer.

What full access does not change:

- The route check. It stays what it is: one question, nothing else.
- The editor context. It is one state for every reader, so an open credential file stays out of it.
- Changing the installation: settings, stored credentials, starting or stopping the connection or the runtime, and the profile itself stay local, because a remote caller could cut its own route.
- Switching on the tools that read or write the memory of other processes (`allowProcessAccess`, `allowMemoryWrite`).
- Whether a task that a connected client hands to a coding agent is run at all (`devmate delegation`, above): that is spent on the owner's account with a provider, and is answered and chosen at the computer.

The `devmate` command line is the owner's interface, and a command a client runs is the owner's process. So every command and agent the runtime starts carries a marker in its environment, and a `devmate` that finds it tells the runtime so: it is then answered as a connected client, and it refuses to stop or reconfigure DevMate, and to be the host a browser starts for the extension (`devmate chrome-host`), which is answered as the owner. A browser that such a command opened carries the marker as well, with every host it starts, and is turned away the same way, the owner's own browser included: the host tells the extension why before it ends, and the panel says to close that browser completely and open it oneself. A model that is told "folders are shared by the owner" and helpfully runs `devmate project add` through its shell tool is refused like its MCP call was. This stops the well-behaved case only. The marker is an environment variable, `DEVMATE_CLIENT_COMMAND`. The `env` input of `shell_run` cannot set or clear it, but the text of a command can, in the same line that then runs `devmate`: that `devmate` is answered as the owner at the computer, `devmate access full` included. A client that removes the marker this way, or reads the owner token and calls the control port itself, is covered by the paragraph on write access above: the guarded profile is a boundary only where every shared project is read only.

The browser extension (Chrome, Edge) gives the runtime the owner's own browser: bookmarks, tabs and windows, history, downloads, the reading list, and the text and a picture of the page in front. That is more personal than a project folder, and it is the owner who connects it: by loading the extension and running `devmate chrome install`, which a client's `devmate` refuses. Once connected, every client that is the owner can read these and, through `capability_call`, change them; nothing of it is tied to a project or held back by a project's protection. The extension reaches the runtime through a native messaging host, a program the browser starts for the one extension id DevMate registers and that refuses to serve any other; no port listens for the browser. The host carries the owner's local token, so the four operations it speaks (`chrome.attach`, `chrome.next`, `chrome.result`, `chrome.detach`) are local only and a connected client cannot pose as a browser. As an entry the extension can ask for the status, a start, a link to the workbench, the MCP address and the number of things that wait for the owner; it cannot stop the runtime or call an operation by name. The owner can pause the browser in the extension: every request is then refused there, and the client is told that this is the owner's decision. The extension keeps a short list of what was asked of the browser (the method, the time, the outcome), in the browser and without the content. Text read from a page is marked untrusted: it is data, never instructions, and it is the client's own care that keeps it so.

The extension can also debug a page as DevTools does (`chrome.page.*`), through the browser's debugger: read the console, the network with headers and bodies, the elements and what the page stores, and click, type, run a script, answer a dialog. This works on any tab the owner has open, signed in as they are, so a script run there can do whatever the owner could do on that site. What stands between that and a client: everything that acts is a change and goes through `capability_call`, which a client asks its user about; the values a page stores (cookies among them) are refused to `capability_query` and given only through `capability_call`; the browser shows its own bar on a tab for as long as it is debugged; the owner can pause the browser in the extension; and the debugger leaves a tab after five minutes without a call. What does not stand in the way: a client that is the owner and does not ask (full access, or a client without confirmations), and a page whose text persuades a model to act on another tab. A tab behind another, or in a minimized window, is acted on and pictured where it is, without being brought to the front: of that the owner sees nothing on their screen but the browser's bar on that tab. For it the page is told that it has the focus: after the mouse or the keys were used on it, for as long as the tab is debugged; for a picture, which is a read, only while the picture is taken. A site may then mark what it shows as read, or go on playing. What the extension asks a page about itself is not run as done by the page's user; only what a client has the page do is (`chrome.page.evaluate`, `chrome.page.select`), so a read cannot open a window or write to the clipboard in the user's name. Finding an element by its text, and waiting for a text, never look at what a password field holds: a read could otherwise be used to guess a password a character at a time. `page.inspect` shows the value a password field has in its markup as `(hidden)`. A CSS selector is the caller's own and is not looked into: where a page writes a password into the `value` attribute of its markup, a selector that tests that attribute can still ask about it.

Two kinds of tabs are not read, worked or sent elsewhere through the browser at all. One is DevMate's own workbench: a local page on the port the runtime answers the owner on, or one that calls itself DevMate Workbench. What is decided there (what an agent asks for, whether a task is handed to a coding agent, the access profile) is the owner's to decide at the computer, the page is signed in as the owner at the computer, and a client that could click or run a script in that tab would be deciding for them. The other is a page of the extension itself, where a script has the extension's own powers. Every method that reads or works a page refuses these tabs, `tabs.navigate` leaves them where they are, and a tab that is being debugged is let go the moment the browser says it is on its way to one. The tabs are still listed, and can be closed or reloaded, which decides nothing. A request's headers and body, read through `chrome.page.networkRequest`, can carry credentials as well and are a read; use the browser extension with clients you would let read what you read.

With full access the last distance between "can reach `/mcp` as the owner" and "is the owner at the keyboard" is gone. With `auth.mode: none` on a public address that is everyone who learns the address; `devmate doctor` reports this combination as a warning.

Command lines are shown in process lists and recorded in a project's activity without the credentials written inline in them; the command that runs is unchanged. This recognises well-known forms only and is not a guarantee. A job keeps its exact command, so that it can run and be retried, and shows it as it is. The variables a command job was given are kept with it for the same reason, in the private state database like every job, and are shown by name only: `job.read`, `job.list` and the journal of events never hold their values.

Credential-like files (`.env`, key files, `.npmrc` and similar) are withheld from the file tools by default and can be enabled per project by the owner. Git status names them, marked as protected, so they are not committed by accident; their content is never returned. The read-only Git tools accept only commits as revisions and never run a program the repository configures (filters, textconv, external diff). Executables DevMate starts itself are resolved to absolute paths on `PATH`, never in the project directory.

Each shared folder is read only or writable, as the owner set it. File operations check canonical project paths and exclude the runtime control directory. Reading and listing follow a link or junction only when its target is still inside the project, and judge that target: a link is never a way out of the project or around the credential protection. Nothing is written, moved or deleted through a link, and a file with a second name (a hard link) is read but never changed. File writes can require the hash observed when the file was read.

Write access is trusted local execution authority. Commands, native agents and domain engines may run with the host account's filesystem and network privileges. A project working directory or an API path check is not an operating-system sandbox. Share a folder as writable only with a client you trust; use an independently configured isolation boundary when that is required.

Configured external MCP servers may have independent machine-wide credentials and resources, and a connected client reaches them through any shared project. Third-party annotations do not establish an authorization boundary.

## Native sessions and decisions

DevMate uses documented native provider interfaces and owns the processes it starts. It does not guess private desktop IPC, scrape web sessions, manufacture vendor account tokens or silently attach arbitrary existing sessions.

A session's communication token is restricted to its project/workflow and communication operations. It cannot choose another sender identity or resolve a user approval. Model-origin messages do not become user authorization.

Approvals retain the native options and return the selected option to the waiting request. Form answers are validated against the original request schema and returned to that request. Answer content is not persisted as an input response record. Requested form schemas and surrounding model/provider messages can still contain sensitive context; treat the private runtime database and logs accordingly.

Server-Sent Events are delivered from the journal by cursor: a slow reader pauses its own stream and nothing is buffered for it, so it can neither lose events nor grow the runtime's memory. A reader that stays blocked is released and resumes from its cursor when it reconnects.

An agent started with `isolate` works in a copy of the project: a Git worktree of the last commit on a branch named `devmate/copy-…` in the project's own repository. The copy is kept beside the instance directory and never inside it, so the owner token and the stored credentials are not in a folder above the one the agent works in. What the copy proposes is worked out in an index of its own; the copy's index, which the agent may be using, is not touched. Git runs there with the repository's hooks switched off. The copy keeps the agent's file changes away from the project until they are applied; it is not a sandbox: the agent's commands run with the owner's account as they do anywhere, and its permission requests are asked as usual. Applying needs write access and brings the work in as uncommitted changes, all of it or none; a change to a file the project protects stops the whole application. What is replaced is kept first, and the changes are recorded in the history like any other, so they can be taken back. A copy is removed when its work is applied or discarded and when its project is taken out of DevMate.

A queued command or capability job checks immediately before the native effect that its project is still shared, and still writable when the job changes something. Cancellation cannot undo side effects that were already produced.

## Jobs and process ownership

Queued, running, completed, failed, cancelled and unknown outcomes are distinct. Interrupted execution is not silently replayed. Explicit retry creates a new execution record.

Cancellation is only reported as confirmed when the relevant native protocol or owned process provides the evidence. Failed cleanup retains owned resources for an explicit retry. CLI stop validates instance, generation, process and build identity; a PID read from a record is not sufficient authority to kill a process.

A runtime or project close drains owned jobs, capability clients, browsers and vault operations before disposing of their records. Host record writes needed by an already-running vault operation may finish during that drain through the locally authenticated, bound host interface.

## State and credentials

Each DevMate 4 instance uses its own SQLite database and private runtime records. Old instance state is not imported. Owner tokens, OAuth signing material, native session communication tokens, third-party MCP credentials and tunnel runtime keys belong to the local owner.

Connection credentials are stored in the private instance directory (`devmate secret set`, read from standard input), in the file `secrets.json`, and handed only to the connector process that needs them. That file is not encrypted: what protects it is the privacy of the instance directory (the owner's profile on Windows, mode 0700 elsewhere), the same thing that protects the owner token and the state database. Whoever can read the owner's files can read these credentials; they are not placed in the environment project commands inherit and no operation returns them. A connector the runtime started is recorded so that a runtime which died without stopping it does not leave it running; only that exact process is ended, identified by program and start time. Do not publish runtime state, private project content, bearer tokens, login codes, raw provider logs or credentials in source, issues, screenshots or test fixtures. Third-party tool results and provider messages remain untrusted input.

## Obsidian and domain tools

Vault operations use the public Obsidian APIs through an explicitly attached desktop host. Batch previews, saved operation records and rollback apply to the documented vault operations; they do not undo arbitrary external commands. Disconnecting an HTTP request does not undo a native Vault operation already executing.

Browser and reverse-engineering tools require explicit project and local tool configuration. Their execution authority and optional native dependencies must be assessed as part of granting write access. Tests that skip an absent native backend do not prove that backend works on the deployment machine.

## Dependencies and verification

Review production dependency additions according to `AGENTS.md`. Use the official MCP and MCP Apps SDKs and package the third-party notices generated from the actual bundle. Keep native protocol versions and account readiness separate from package build success.

Protocol, per-request identity, project access, file writes, job outcomes, process cleanup, host drains and UI wiring are exercised by the current runtime test suites. See [STATUS.md](docs/STATUS.md) for what is not done yet and what could not be verified without real accounts and deployments.

## Reporting vulnerabilities

Only the latest release receives security fixes.

Report suspected security vulnerabilities privately through GitHub's [Report a vulnerability](https://github.com/Kukutx/DevMate/security/advisories/new) flow. Do not open a public issue for an undisclosed vulnerability.

## Known limits

- **Write access is full access.** See "Project access and trusted execution": a client with one writable project can act as the owner's operating-system account. DevMate has no sandbox.
- DevMate is connected to an account at a client, not to a person. Everyone who uses that account (a ChatGPT account shared with someone, for instance) calls it as the owner.
- What tells a `devmate` command started by a client from one the owner typed is a marker in the environment (`DEVMATE_CLIENT_COMMAND`). It keeps a client that means well from doing through `devmate` what is the owner's to do at the computer. It is not a boundary against a client that runs commands, and cannot be one: such a client acts as the owner's account, can clear the marker in the command it runs, and can then switch on full access by itself. The boundary is whether a client is given a writable project at all.
- The runtime keeps running after the editor that started it is closed, until it is stopped (`devmate stop`, or **Stop DevMate Runtime** in the editor). A public connection stays up with it.
- An origin added to `allowedOrigins` may call the local MCP port from a browser, and on that port a caller without credentials is the owner. Add only the origin of a client you run yourself.
- A delegated Gemini CLI or Grok CLI session also loads the MCP servers configured in that CLI's own settings; DevMate cannot keep them out (it does for Codex and Claude Code). If DevMate itself is registered there, the delegated agent reaches it with the owner's authority.
- For a delegated Codex session, keeping the owner's MCP servers out means switching each of them off by name and switching off Codex's apps and plugins as well, because those bring MCP servers of their own: such a session has no plugins. After the start DevMate asks Codex which servers the session reaches and does not go on if there is one it did not provide. `inheritMcpServers` for Codex leaves a delegated session as the owner configured Codex, with all of them.
- A command still running when the runtime dies is ended by the next runtime of that instance, if it had been running for more than a few seconds; a shorter one is not tracked and ends on its own. Processes a command left in the background after it exited itself are not tracked.
- Command redaction, protected paths and the read-only tools reduce what a connected model can see or do by accident. They are not a sandbox: commands run as the owner's operating-system account.
