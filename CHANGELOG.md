# Changelog

## 4.0.6
- **A default changed: a task your client hands to a coding agent waits for your word.** Codex, Claude Code and the other agents run on your account with their provider, so a task that a connected client hands to one (`agents_delegate`, `agents.start` with a prompt, `agents.send`, a message or an assigned task for an agent) now waits until you allow it at this computer, in the workbench (`devmate ui`) or your editor. Starting an agent's process again (`agents.resume`) is refused to a client while you are asked (a task that you allow starts it), and adding to a task that runs (`agents.steer`) unless you allowed that agent's later tasks. That holds in both access profiles: full access does not let the client answer it. `devmate delegation allow` ends the asking, `devmate delegation off` refuses such tasks, `devmate delegation` says which it is (operations `delegation.read` and `delegation.update`; the second only at this computer). What you start here yourself is never asked about. While a task waits no process is started for it (a copy of the project that the client asked for with `isolate` is made before you are asked, and removed again when you say no), it counts against nothing and the agent's other work goes on; you are shown what you agree to (the task as the agent will be given it, the model, a session of the provider it would take up again); a yes for a task that cannot begin right now is not used up: the answer is refused with what is in the way, and the question stays; "this agent's later tasks too" lasts while the agent stays connected; at most twenty tasks wait at once. A client that asks after such a task is told that it waits for you; where you chose not to be asked and something else keeps a task from beginning, it is told that instead, and the task goes when that is out of the way.
- **Update every entry.** An instance this release has used is refused by an entry that is still 4.0.5 (an extension or plugin that was not updated, an old `devmate`): it cannot start the runtime and says which releases are involved, and it still joins a runtime that is running. A 4.0.5 runtime would run a client's tasks without asking where you had chosen to be asked. For the same reason an instance cannot go back to 4.0.5.
- **OpenAI's tunnel beside a public address.** A route that has an address (a relay, a Cloudflare tunnel, your own HTTPS proxy) and OpenAI's tunnel can be open at the same time: `--openai-tunnel <id>` on `devmate connect`, or `devmate connect beside --openai-tunnel <id> | none` to add it to the route there is or take it away (setting `openaiTunnel`). Each way in is served as itself, `connection_status` says which way a request came (`via`) and how the tunnel is doing, and the doctor has lines of its own for it.
- **The browser extension works where it did not.** A tab behind another, or in a window that is minimized or covered, is clicked, typed into, scrolled and pictured where it is; before, the browser said a click or a key was given and the page never got it. A page built of web components (shadow DOM) is clicked, found by its text and waited for like any other, and a frame of a page (iframe) is listed with its address. A dialog that comes up during any step ends the call at once, and the answer says what was really done (`typed`). A browser that was ended is noticed within seconds: a look that names nothing of that browser goes to the one that is still there, and a change, or a call that names a tab or a bookmark by its id, that waited for the browser that ended is given back and not carried out in another. (A call made after that goes to the browser that is connected then, and ids are each browser's own: list again before naming one.) DevMate's own workbench page is refused to the browser's tools, which do not read it, work it or go to it; a click that was already sent in the instant a tab arrives there cannot be ruled out. What waits for you is told to the extension as a number only.
- New in the tools: `capability_list` and `operations_list` find by words (`query`), and `operations_list` looks several operations up in one call (`names`); a command takes variables of its own (`env` on `shell_run`, `exec_command`, `bash`); `workspace_write` adds to the end of a file (`append`), which a log another program is writing needs; `job.read` waits for a job to end (`waitMs`) instead of being asked again and again, and a running command job says which process to read its output from.
- **`exec_command` gives a command no standard input unless it is asked for (`tty: true`).** With an input nobody closed, everything that reads its input when it is given no file (`rg` without a path, `findstr`, `sort`, `python`) waited for the whole time limit and ran on. Other surfaces already worked this way.
- Finding and searching are several times faster on large trees: ripgrep reads on all cores, and is ended once it has reported more than is ever shown. A search for a common word across dependencies took over ten seconds and takes a third of one. The order of what is shown is unchanged. What is new to see: where more matches than is ever taken (two megabytes of ripgrep's output), what is shown is a part of it, marked `truncated`, and not the same part every time; narrow the query or the path for all of it. `project_overview`, `show_changes`, directory listings and taking back a stretch of work each ask the system and the history fewer questions, and the runtime no longer tidies its history while it starts.
- On Windows a change to a file is not refused because another program has it open for a moment or keeps it open while it can still be moved aside; one that cannot be moved either is refused, now after twenty seconds of trying and by a name of its own (`file_busy`). A file that could be neither replaced nor put back says where its content is (`file_displaced`). A file that is marked read-only is left as it is and named as that (`read_only_file`). A folder that could be deleted only in part says what is left (`delete_incomplete`).
- Work a delegated agent did in a copy of the project: it is read and applied where DevMate is installed as it comes, where Codex has MCP servers and plugins of its own, and where Git still watches the copy; work Git could write only a part of is taken out again (`apply_failed`; where a part of it could not be taken out either, the answer names it: `apply_incomplete`), files keep their mode, and a project that is one folder of a larger repository is told that it gets no copy instead of losing the work (`not_repository_root`).
- After an update the command line says when an older runtime is still the one that runs (`devmate start`, `status`, `doctor`, and a command that runtime has never heard of), with the way out: `devmate restart`. A restart keeps the port the runtime ran on.
- Said plainly where it was not: a shared folder that was moved or deleted (by the call that needs it, a task for an agent that is already connected among them, by the doctor, and where projects are listed for a client and on the command line, `project_list` and `devmate project list`, from the first answer of a runtime on; the workbench and the editors do not mark it yet); a port that is taken, with how to choose another; a proxy that does not pass the public host name on; a public address that could not be reached from this computer, which is not the same as a client in the cloud failing; where credential-file protection is lifted; what `relay setup` needs when key login is set up already; which Node an editor tried and what each said; where the one-time sign-in code comes from; JSON after `--json` that a Windows shell took the quotes out of (`--file` works there). The doctor now runs a one-line command through PowerShell and says when a policy forbids scripts.
- **DevMate starts where PowerShell 7 was installed with winget, and uses it.** `winget install --id Microsoft.PowerShell`, the command the doctor gives, now installs PowerShell 7 as an app package, and `pwsh.exe` is then a name Windows keeps on PATH for it (an app execution alias), not a file. DevMate stopped at that name while looking for the shell, and the runtime did not start. Such a name is found and started now, for the shell and for every program looked up on PATH, and a name on PATH that cannot be looked at is passed over.
- **The browser extension reaches DevMate where your home folder is not written in ASCII (Windows).** What the browser starts is a command file, and Windows read the paths in it in the code page of the system: with a home folder, an instance or DevMate itself under a name in Chinese, nothing was started and the extension could only say that DevMate was not there. The file now says how it is to be read; the next start of the runtime writes it anew.
- A runtime that ended on an error of its own counts as one that ended unexpectedly: an editor that keeps the runtime running starts it again (at most three times in ten minutes, as after a crash), and `devmate status` says `crashed`. Before, it was a plain "stopped", and no entry started it again for having ended that way.
- The port belongs to the instance, not to the entry that starts it. The port a runtime ran on is written down in the instance directory, and every start that names none takes it: a restart from an editor, the browser starting DevMate, a plain `devmate start`, after a stop and after an unexpected end. Before, each entry started the runtime on the port of its own settings, and a runtime that had been started on another one moved, away from the clients on this computer and the route of a tunnel. A port you name wins and is the one kept from then on: `--port`, or a port you set in an editor's settings (any number; 8788 there is how an editor goes back to the usual one, and VS Code's setting is empty unless you set it, so that 8788 typed in its Settings page is kept). From the command line: `devmate restart --port 8788`. An Obsidian vault whose settings an earlier plugin saved shows 8788 in the port field and so names it: empty the field to follow the instance.
- A runtime whose own folder was removed while it ran says so until it is started again. An update of the VS Code extension removes the folder of the version before; the runtime that was started from it answered on, and tasks for coding agents, Claude Code's permission requests and the browser's connection failed with nothing that said why. `devmate doctor` now has a failing line for it (`runtime.files`), `devmate status` and `start` say it, and so do VS Code, Obsidian and the browser extension's host.
- VS Code and Obsidian no longer take a runtime that is busy for one that stopped. A runtime that holds its instance and does not answer within a moment kept its process, and the editor let go of its folders (and of the endpoint its own tools use) until the next look; now it stays as it is and says "busy". A runtime that ended by itself is shown as "stopped unexpectedly", not as stopped.
- The program a browser starts for the extension ends when an update of DevMate replaced it, so that the browser starts the new one. Before, it lived as long as the browser and went on speaking for the DevMate that was installed when the browser was opened.
- **Where several browsers are connected, you say which one DevMate uses.** It uses one at a time: the one that connected last, or the one you chose since. A browser you paused is passed over for one that is not; before, a paused browser that had connected last was asked every time and refused every time. Once another browser is used, a call that names a tab, a window, a bookmark or an element by its id is refused with the reason instead of being handed to it: the same id is something else there. So is such a call while several browsers are connected and none has answered since DevMate started (after a restart your choice is forgotten): look first, then call again. With one browser nothing changes. The panel of the extension says how many are connected and whether this is the one, within a moment of a change, and has "Use this browser" (it lifts no pause). `devmate doctor` names the other browsers and warns when the one in use is paused, and the Now page of the workbench lists each with whether it is in use or paused.
- The browser extension says more of what is the matter: why a start "with the browser" did not work, in DevMate's own words; that the running DevMate lost the files it was started from and has to be restarted; and it notices a host that is there and answers nothing (asked once a minute, let go after thirty seconds without any answer, and the browser starts another).
- A relay that does not answer holds the start of the runtime up for five seconds, not for the fifteen to twenty that cost local use its start as well.
- **The workbench has a page for everything that is going on (Now):** running commands, agents at work, queued and running jobs and what waits for you, across all projects and without choosing one, each with the way to stop it; and who is attached (editor windows, the browsers, the route from outside). It is the owner's page at the computer: a workbench inside a client's conversation does not have it, and a connected client cannot call `runtime.now`, in either access profile.
- **DevMate notes who asked for each change.** Every call that changes something leaves one line in the journal when it ends: which operation, who asked (you at this computer, you in an editor window, or a connected client by the name it gave itself and the way it came: on this computer, through the public address, through the tunnel of OpenAI), whether it went through (with the error's code where it did not), and how long it took. Nothing of what the call carried is kept: no command, no path, no text; only, where it has the form of a name, which capability was called or which operation a call by name asked for. The Now page lists the clients since DevMate started and the last fifty changes; a project's activity shows these lines among its events (`operation.called`, also in `event.list`). A call that only reads is not noted, nor is what an editor or the browser's host asks in the background. The name is what a client says of itself and proves nothing.
- The workbench and the panel of the browser extension have a neutral look: near-black on white (and the reverse in the dark theme), thin borders, a quiet shadow, and colour only where it says something (good, warning, danger). What they do and what they say is unchanged.
- The workbench served on this computer cannot be held in a frame by another page.
- A notification in VS Code cannot hold a link that DevMate did not write. VS Code makes a link of a label in square brackets that is followed by an address in round brackets, in the text of a notification, and a link that names a command runs it when it is clicked; what an agent asks was shown there as it came, so a repository an agent read could put such a link before you. No text DevMate hands to a notification can form one now.
- What `devmate` writes in your terminal holds no character the terminal acts on, other than the line end and the tab. A name a client gave a project, or an operation it asked for, was written as it came by `devmate doctor`, `doctor --report` and `logs`: with the characters that move the cursor or wipe a line it could take a line of the report away and put its own there. Such characters are written by their numbers (`\u001b`), also in what is printed as JSON and in what a runtime started with `devmate serve` writes into that terminal by itself; an entry of the doctor is one line wherever it is shown, and a name somebody else chose stands in it in quotes, cut short.
- The report for a bug (`devmate doctor --report`) is the same report whatever a project is called. A project's name was taken out of the whole text, the report's own marks and headings with it (a project called `ok ] node` took the mark off an entry), and before the addresses were: a project called `acme` left `bob@` of `bob@acme.com` standing, and the public host did the same to the account on your own server in what OpenSSH said (`deploy@relay.example.com`). Now what an entry says, each failure and each line of the log is cleaned by itself, what gives somebody away goes first, the host and then the name last, and a name told as the doctor tells it is taken out as well. What the report cuts short (a line of the log, the message of a failure) it has cleaned first, and a line of the log it could read only the end of is left out.
- `devmate chrome-host`, which a browser starts for the extension, refuses to start from a command of a connected client: it was answered as the owner there. A browser that such a command opened is turned away as well, and the extension says why and what to do (close the browser completely and open it yourself).
- For a client and for scripts, what else is new to meet:
  - an agent's status `unstarted` (written down by a client, not started), a delivery's status `held` (waits for the owner's word), and the refusals `delegation_ask`, `delegation_off`, `delegation_backlog`, `delegation_declined`, `agent_never_ran`, `project_missing`, `copy_missing` (an agent's copy that was deleted by hand) and `project_removed` (a task that waited in a project that was then taken out of sharing), beside those named above for files and for an agent's copy;
  - with `devmate delegation off` the tools that hand a task to an agent are not offered to a client at all (`agents.delegate`, `agents.start`, `agents.send`, `agents.steer`, `agents.resume`, `message.send`);
  - a client's message to an agent is named "Connected client", not "You", and is in the agent's inbox only once it was given to it;
  - `approval.cancel` on a question about a client's task (kind `delegation`) takes the task back; `approval.resolve` on it is answered at the owner's computer only;
  - `delegation.update` answers with what it did to the tasks there were (`allowed`, `waiting`, `again`, `ended`), and a task that waits although you are not asked says what for (`waits`);
  - `project_list` marks a project whose folder is not there (`missing`); the doctor has a line for folders that do not answer (`projects.unanswered`), and its line about an address over SSH that is not reached carries what OpenSSH said last;
  - a capability job in a project whose folder is not there ends as `failed` with the outcome `not_started`;
  - records carry `client` (an agent a connected client started), `delegationAllowed` (an agent whose later tasks you let through) and `delegated` (a workflow made for one task a client handed over); OpenAI's tunnel can say `no_answer` (a request for work was not answered in time) beside `unreachable`;
  - `env`: a name that begins with `DEVMATE_` is refused, and at most 64 variables are taken; on Windows the Claude surface's command tool is `powershell`, which takes `env` too; `job.start`, `job.read` and `job.list` show a command job's variables by name only;
  - `operations_list` with `names` answers `unknown` for a name that is no operation;
  - where OpenAI's tunnel runs beside an address that requires sign-in, what comes through the tunnel is not asked to sign in: who may use the tunnel is decided in the OpenAI account it belongs to;
  - `devmate relay remove` makes a tunnel that ran beside the relay the connection; `devmate connect ssh` keeps `--ssh-port` and `--identity`, and every `connect` refuses an option that names something another kind of connection has;
  - `workbench_call` also takes `job.cancel`;
  - the state carries the format number 1 (see "Update every entry").

## 4.0.5
- **Your own browser, through an extension for Chrome and Edge.** DevMate could already drive a browser of its own; now your client reaches the one you use: bookmarks (tree, search, create, rename, move, remove), tabs and windows (list, open, go to, bring to front, reload, close, move, group), history (search, delete), downloads (list, start), recently closed tabs (list, bring back), the reading list, the most visited sites, and a tab's page (its text, a picture of what it shows or of the whole page). **It debugs a page like DevTools**: the console and uncaught errors, the network requests and one of them in full, the page as its elements with a number to act on each, one element in detail, what the page stores, click, type, press, choose, hover, scroll, run a script, answer a dialog, reload, and emulation of a screen, a color scheme or being offline; Chrome shows its own bar on a tab while it is debugged. They are capabilities of the engine `chrome`, used through `capability_list`, `capability_query` and `capability_call` without a project. The extension is also an entry like the editors: its panel says how things stand and what to do about it, starts DevMate, opens the workbench, copies the address a client needs, counts what waits for you and lists what DevMate did in the browser. It has two switches: **Let DevMate use this browser** (off: every request is refused and the client is told you paused it) and **Start DevMate with the browser** (off until you turn it on). It is loaded once, from a folder in DevMate's instance directory that stays where it is: every start of the runtime makes that folder, and the program the browser starts, the DevMate that runs, and the extension loads itself again when its files changed, so an update through any entry needs nothing done in the browser (Developer mode stays on). `devmate chrome install` registers DevMate with Chrome and Edge for your account (no administrator) and puts the extension into that folder, `devmate chrome` and the doctor say whether a browser is connected, `devmate chrome uninstall` takes it away. The browser starts DevMate's own small program for this one extension (native messaging): nothing listens for it and no public connection is needed.
- **OpenAI's tunnel without a second program:** `devmate connect openai-tunnel --tunnel-id <id>` is all it takes. DevMate speaks the tunnel's published protocol itself: this computer only reaches out to `api.openai.com`, nothing is installed or downloaded, up to 32 calls are served at once (`maxConcurrentRequests`), progress is passed on while a call runs, and the tunnel id in ChatGPT never changes. The doctor says whether OpenAI accepts the key and how many calls have arrived. A refusal is repeated in OpenAI's words with what to do about it: the key, the tunnel id, the tunnel's organization (`--organization <id>`), or an update when the protocol version is no longer taken. A tunnel that is connected but not offered in ChatGPT is said to be a matter of the OpenAI account, with the place where OpenAI explains it. OpenAI's own `tunnel-client` is used instead where `--executable` names it.
- **A relay of your own:** `devmate relay setup user@host [--domain <name>]` makes a public Linux server you control the way in. It installs Caddy there over your SSH key login, forwards one path nobody can guess to this computer through an OpenSSH remote forward, and by default answers only the addresses ChatGPT and Claude connect from and this computer. The address stays, answers stream, and nothing of a third party is in between. Reached by the server's address instead of a name, it needs Caddy 2.10: where the system's package is older or missing, the setup takes Caddy from Caddy's own package repository, and a Caddy that was there before is left alone, with the commands that would replace it. A relay has no sign-in (it forwards one path only), and setting both is refused. `devmate relay remove user@host` takes it off again.
- What the runtime itself asks of the outside (OpenAI's tunnel service, the check of its public route, a signing-in client's metadata document, external MCP servers) goes through the proxy the computer is set to use: the `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` variables, or on Windows the system proxy of the account, followed within a minute when it is switched. `devmate doctor` says which proxy is in force and names a setting it cannot use.
- A model is shown its tools under the names it knows: ChatGPT and Codex get `read`, `apply_patch`, `exec_command` and `write_stdin`; Claude gets `read`, `write`, `edit` and `bash` (called `powershell` where commands run in PowerShell, so that the name never promises another shell); other clients get DevMate's own names. The client is recognised by what it says it is, or chosen with `?tools=` in the MCP address, and `devmate doctor` says what the last client called itself, which list it was shown and why; every tool stays callable whatever list was shown. Everything that only reads, the capability tools and taking a change back are on every list; making a folder, moving and deleting are operations behind `operations_call`, which a patch or a command does as well.
- `workspace_patch` changes several files with one patch, all of it or none: the `*** Begin Patch` envelope Codex writes (update, add, delete, move) or a unified diff as `git diff` prints it (renames and quoted names included). A hunk is found by its text, so stale line numbers, differing indentation and typographic quotes do not stop it; one that fits nowhere is refused with the line where it stops matching, and one that fits in two places is refused instead of guessed. Should a write fail halfway, what was already written is taken back. Each file stays restorable and the whole patch is taken back with one `workspace_restore`.
- `show_changes` says what is uncommitted in a Git project, whoever changed it: per file what happened and how many lines came and went. Marked as reviewed, the next look shows only what changed since, and nothing when nothing did.
- **A delegated agent can work in a copy of the project.** `agents_delegate` with `isolate:true` starts the agent in a Git worktree of the last commit. The project does not change until its work is read (`agents.proposal`) and applied (`agents.apply`: all of it as uncommitted changes, or none of it when the project changed in the same places meanwhile) or discarded (`agents.discard`). Applied work is in the history, so it can be taken back like any other change; a link it brought is applied and named as the one thing that is not. The copy is kept beside DevMate's instance directory, never inside it.
- **One call takes back a stretch of work.** `workspace_restore` with `since` (the number of a `workspace_history` entry, shown there as `#N`) takes back every change DevMate's file tools made after that entry, newest first. A file something else changed in the meantime is left alone and listed, and taking back can itself be taken back.
- DevMate has one owner and no other accounts. Member accounts are gone, with their roles and their per-project grants: a sign-in that was issued to a member is refused, and every agent, command and job is the owner's. OAuth sign-in on a public address proves that the client is the owner's; the check DevMate makes of its own public route is the only other caller, and it is told which runtime answers and nothing else.
- A command runs without a terminal: nothing waits in a pager or at a prompt and no colour codes are written (`NO_COLOR`, `TERM=dumb`, `PAGER`, `GIT_PAGER`, `GH_PAGER`, `GIT_TERMINAL_PROMPT`), unless the owner's own environment says otherwise.
- The doctor says when this computer has no public address of its own and which routes work then, and what Windows PowerShell 5.1 costs with every command.
- `runtime.metrics` says for every operation how often it was called, by whom, how long half of the calls and nineteen in twenty took, and which errors it returned, and lists the newest failures.
- `devmate doctor --report` prints one text for a bug report: the checks, how the operations went, the newest failures and the last log lines, with credentials, private paths, account names and addresses taken out.
- A call that names no project while several are shared says in its answer which project it was answered from.
- What a connected client is told about the connection (`connection_status` with full access) never repeats the key a quick tunnel address ends in.
- A long-running capability is started with `operations_call {operation:"job.start", …}` and read with `operations_query {operation:"job.read", …}`.
- What every tool tells a client about itself (read-only, destructive, reaching outside) is part of the recorded public surface, so such a hint cannot change by accident.
