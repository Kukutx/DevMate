# DevMate 4.0 全面审计台账

审计日期 2026-10-09，修复与回填 2026-10-10。

七条互不重叠的审计线路逐文件读完了 3.8.9 与 4.0 的全部代码，并对照了当日的官方文档。每条发现都带文件行号证据，标注为“实测”的由探针脚本在真实运行时上复现。

状态说明：

- `已修`：已改代码，并有自动化测试覆盖。
- `已修·未实测`：已改代码并有测试，但对应的真实外部环境（真实客户端、真实账号、真实隧道）没法在本机验证。
- `部分`：主要问题已解决，后面写明还剩什么。
- `未做`：没有处理，后面写明原因。
- `不做`：有意不采纳，后面写明理由。

编号前缀：X 执行与文件，C 运行时核心，A Agent 层，E 引擎与 Obsidian，H 宿主/界面/打包/文档/测试，O 官方对齐，G 相对 3.x 的缺口。

验证结果（2026-10-10，全部修复之后，Windows 11，Node 24.21）：96 个测试文件、710 个用例，706 通过、0 失败、4 个跳过（3 个因未安装可选的 Python 解析库，1 个是只在 POSIX 上有意义的套接字路径用例）；`npm run lint` 无告警；一次构建产出三个安装包（VS Code 扩展、Obsidian 插件、不带依赖的命令行包）并对打包产物做了端到端冒烟；命令行包按用户的方式离线安装后，经 npm 生成的 `devmate` 命令走完了启动、注册项目、读文件、体检、打开工作台、停止的全过程。在真实的 VS Code 1.133 里，用源码和打包后的扩展各跑了一遍“两个独立实例加一个额外窗口同时自动启动”：三个文件夹零点击即以读写共享；在窗口里把其中一个改成只读后它立即拒绝写入，另外两个不受影响，窗口重新绑定后也没有被改回去；把 ripgrep 从 PATH 上拿掉后，查找文件改用编辑器自带的那一份照常工作。Claude Code 2.1.293 经 HTTP 和经 `devmate mcp`（stdio）都显示已连接（用隔离的配置目录，没有发送任何提示）；Codex 0.161.0 接受了 `codex mcp add devmate --url …`，但它的列表不做连通检查，只能算验证了配置格式。

Linux 上的验证（2026-10-10，Ubuntu 24.04 的 WSL 发行版，Node 24.21，以无特权用户、不带任何 Windows 路径的环境运行）：`npm run lint` 无告警；96 个测试文件、705 个用例，681 通过、0 失败、24 个跳过（都是只在 Windows 上有意义的用例和未安装的可选组件）；最后的代码状态跑了全量测试，结束后没有残留进程和临时目录；`npm run candidate` 产出三个安装包并通过打包后的冒烟。另有一组只能在真实 POSIX 上做的检查：命令确实在 bash 里运行，`[[ ]]`、`source`、`pipefail` 可用；一个忽略 SIGTERM 的子进程连同它的进程组在约 2.5 秒内被结束并得到确认；把文件当目录用得到 `not_directory`；实例目录权限 700、令牌文件 600；运行时被 `kill -9` 之后留下的套接字，由三个同时启动者中的恰好一个接管，只出现一个运行时；正常停止后套接字被删除。macOS 没有运行过。

第三轮起，“多个真实 VS Code 同时启动、共用一个运行时”这项检查进入了仓库（`npm run test:vscode-host`，CI 和发布流程都会跑）：两个独立的编辑器实例加第三个窗口同时自动启动，三个文件夹零点击即以读写共享，在窗口里把其中一个改成只读后写入被拒，窗口重新绑定后不被改回，关闭全部编辑器后运行时仍在。它在扩展声明支持的最低版本 VS Code 1.101.0 和较新的 1.133.0 上都通过（源码形态）。候选包一次构建产出发布所需的全部文件：VS Code 扩展（含更新日志与中英文本地化文件）、Obsidian 插件的压缩包及其三个单独文件、命令行包、校验和；模型可见的工具为 36 个。

### Linux 实跑与性能测量（L）

全量测试第一次在真实的 Linux 上运行，以及随后的性能测量，又查出下面这些。它们不在上面的 80 条之内。

| 编号 | 级别 | 问题 | 状态 |
|---|---|---|---|
| L1 | 中 | 路径中间的一段其实是文件时（`file.txt/inside.txt`），POSIX 上 `lstat` 报 `ENOTDIR`，原样抛给了模型；Windows 上同样的输入得到的是另一个错误码，所以之前没有暴露 | 已修：统一报 `not_directory` 并指出是哪一段。两个系统上都有用例 |
| L2 | 中 | VS Code 宿主的自动启动在激活之后还会被后来的事件再次触发，和用户的停止相互竞争：已经停掉的运行时可能被重新拉起。测试里表现为用例结束后还留着一个在默认端口上监听的运行时 | 已修：自动启动只发生在编辑器激活时；工作区当时还没有被信任的，在授予信任的那一刻补做一次。之后任何设置或文件夹变化都不会再启动一个被停掉的运行时 |
| L3 | 低中 | Windows 上刚写完的文件常被杀毒软件或索引器短暂占着，原子替换的 `rename` 偶尔以 `EPERM` 失败，一次 `workspace_write` 就这样报错（全量测试里偶发） | 已修：替换在 Windows 上对 `EPERM`、`EBUSY`、`EACCES` 短暂重试（累计不到半秒），其他系统和其他错误立即失败。状态文件的原子写入用的是同一个函数 |
| L4 | 低 | 一个只在 POSIX 上执行的测试断言用的是改名之前的浏览器配置目录；事件流用例依赖固定的 20 毫秒等待，慢机器上不稳 | 已修：断言对齐现在的目录；事件流用例改为按事件循环的轮次等待 |
| L5 | 低 | 第一次在 Linux 上运行时，`command-process` 的中止用例和 `engine-state-isolation` 各失败过一次；另外 Windows 上一个浏览器用例在固定的时间窗口上失败过一次 | 未定位：之后 Linux 上连续 5 遍、Windows 上 2 遍全量运行都没有再出现，没有找到原因，也没有改动这三个用例。如果在 CI 里再次出现，应当按时间敏感的用例来查 |
| L6 | 性能 | `workspace_find` 对每个命中的文件都从项目根开始逐级重新核对一遍路径：两千个文件的仓库里，同样的几个目录被问了几千次，一次查找 208 毫秒，其中 ripgrep 本身只占 55 毫秒 | 已修：一次调用之内每个目录只核对一次，文件本身仍然逐个核对（硬链接、符号链接、受保护文件的判断不变）；同一次查看同时给出“能否显示”和大小。同一查找降到 89 毫秒 |

## 十、第三轮独立复审与发布流程（2026-10-10）

第二轮修完之后又做了一次复审，这次的重点不是“还有什么没发现”，而是三个新角度：第二轮的修复本身对不对；作为公开发布、上架插件市场的项目，陌生人和市场审核者会看到什么；设计是否绑死在今天的厂商和协议版本上。三条线路互不通气、只读不改，能复现的都写了探针。另外逐项对比了 3.x 与 4.0 的发布流程。

最重要的结论：第二轮宣称的“所有者的决定不可被客户端撤销”并不成立。复审方用探针走通了一条链：经 MCP 新建一个可写项目，在里面运行命令，读出所有者令牌，再用令牌撤销全部决定。根源是没有沙箱：**只要客户端有一个可写项目，它就能以所有者的系统账户做任何事**。这一轮把规则改成与此相符的样子，并在文档里照实写出来：

- 共享哪些文件夹只能在本机决定（编辑器、`devmate project add`、本机工作台）。经 MCP 没有这个工具，通用调用也会拒绝。
- 审批和提问只能在本机回答。上一轮给“声明了 MCP Apps 的宿主”留的例外取消了：那个能力是客户端自己说的。
- 只共享只读项目时，没有命令可运行，上述限制才是真正的边界；`SECURITY.md` 和 README 都这样写了，不再说“约束所有客户端”。

| AU9 | 建议 | 基于 VS Code 的其他编辑器从 Open VSX 安装；`npx` 需要 npm 上有包 | 已备好：两个发布作业已写好，默认关闭，由仓库变量开启。没有运行过 |
| AU10 | 低 | 仓库的标签保护规则只覆盖 `v*` | 已做（所有者批准）：标签保护规则已扩展到 `refs/tags/[0-9]*` |


### 第四批：最后一遍盲区排查（BS）

前三轮都是“审代码”。这一遍换了问法：一个已经装着 3.x 的人更新之后会怎样；一个中文 Windows 用户会怎样；一个远程窗口里的用户会怎样；一个连续运行几周的后台进程会怎样；卸载之后会怎样。

| 编号 | 级别 | 问题 | 状态 |
|---|---|---|---|
| BS1 | 中 | Windows 上不少程序在输出不是终端时用系统编码写（GBK、Shift_JIS 等，Python 即如此），命令输出被当作 UTF-8 解码成乱码 | 已修：不是合法 UTF-8 的行按系统编码读取，逐行判断，所以同一段输出里的 UTF-8 不受影响。中文目录名、文件名、命令文本、Git 提交信息和差异另行实测，全部正确 |
| BS2 | 中 | 远程窗口里打开工作台会被拒：编辑器把端口转发到另一个本机端口号，而控制端口要求 Host 里的端口与自己一致 | 已修：控制端口接受任何本机名加任意端口。防 DNS 重绑定靠的是名字而不是端口号，外来名字照旧拒绝。只有 Host 判断有用例，真实的远程窗口没有实测 |
| BS3 | 中 | 运行时可以连续运行几周，日志只在启动时轮转，运行中无限增长 | 已修：运行中超过 8 MiB 时保留一份旧的并从头开始 |
| BS4 | 低中 | 实例目录被整个删除后，运行时仍在运行，而且谁也停不掉它（测试里出现过这样的孤儿进程） | 已修：运行时每分钟确认实例目录还在，不在了就自行停止。相关用例的清理顺序也改正了 |
| BS5 | 低 | 把文件夹移动到它自己里面，会先在其中创建目标目录，再以系统原始错误失败 | 已修：事先拒绝，什么都不创建 |
| BS6 | 低中 | Windows 上结束进程树时按裸名启动 `taskkill`。裸名也会在当前目录里查找，而命令行的当前目录可能是别人写的文件夹 | 已修：用系统目录下的完整路径 |
| BS7 | 中 | 已经装着 3.x 的用户自动更新到 4.0 之后没有任何说明：旧的 Gateway 可能还占着 8788 端口，连接和 MCP 地址都要重设 | 已修（文档）：README 增加“从 3.x 升级”一节，端口被占时编辑器可以直接打开端口设置。本机的 3.8.9 Gateway 确实占着 8788，测试全程没有碰它。没有写任何读取或迁移 3.x 的代码 |
| BS8 | 低中 | 卸载扩展或插件不会停止运行时，公网连接也还在，而只用编辑器的用户再没有界面去停它 | 已修（文档）：README 增加“卸载”一节。没有在卸载时自动停止：运行时可能还被其他入口使用 |
| BS9 | 低 | `package-lock.json` 里记录的引擎版本与 `package.json` 不一致（上一批改了最低 VS Code 版本） | 已修：重新同步 |
| BS10 | 低 | Linux 上一个用例在全量运行的高负载下再次失败，就是第二轮记为“未定位”的那一类：它在固定等待 150 毫秒后就断言子进程已经输出 | 已修：改为等子进程确认输出已写出。L5 里另外两个偶发失败仍未重现、未定位 |

| BS11 | 中高 | 多个入口同时启动时，没抢到实例的启动者以为自己的进程“已经自行退出”就返回了；机器慢时那个进程其实还在启动途中，等运行时被停止后它会接管实例，于是用户停掉的运行时又活了过来（GitHub 的 Ubuntu 任务上稳定出现，Node 24 和 26 都是；本机和 WSL 上没有出现过） | 已修：加入别人运行时的启动者先结束自己那个尚未退出的进程再返回。有用例模拟一个迟迟没有启动完的进程。这是首次在 GitHub 上运行 CI 查出来的 |

真实 Obsidian 测试查出的问题（OB）：

| 编号 | 级别 | 问题 | 状态 |
|---|---|---|---|
| OB1 | 中 | 先启动运行时再共享库时，当前笔记和选区一直传不到运行时：窗口是在库还不是项目的时候绑定的，之后没有重新绑定（实测复现两次） | 已修：库成为项目后立即重新绑定窗口并发送当前笔记。有回归用例 |
| OB2 | 中 | 端口被占时只弹出一条几秒后消失的提示，文字里有两个句号，也没说去哪里改 | 已修：提示点名“设置 → DevMate → Local port”，并保留到用户关闭 |
| OB3 | 低 | 上一次操作的错误在之后的成功操作旁边一直显示 | 已修：每次操作开始时清除 |
| OB5–OB9 | 低 | 体检把“仅供参考”的项目也算作需要处理；未共享的库在重启后显示成“已分离”；实例目录出错时显示系统原始错误且提示不消失；接受相对路径的实例目录；端口框接受 `0x7000`、`2e4` | 已修 |
| OB10–OB12 | 低 | 焦点在侧栏时发布的行数和选区为空；退出后窗口登记残留最多 5 分钟；状态栏项不显示可点击的光标；停止对话框的说明写的是重启 | 已修 |
| OB4 | 设计 | 共享询问的默认按钮是“读写”，按回车就授予写权限 | 不改：与 VS Code 默认读写共享的决定一致。如果你希望 Obsidian 默认只读，这是一行改动 |


### 第五批：权限档（PF）

起因是所有者的担心：3.x 用的是 `fullAccess` 档，4.0 经过第三轮收紧之后只剩相当于“受保护”的一档。对照 3.8.9 的代码逐项核对，担心成立。

| 编号 | 级别 | 问题 | 状态 |
|---|---|---|---|
| PF1 | 高（体验） | 被派发的 Agent 每一步都要批准，而第三轮之后批准只能在本机做。从 ChatGPT 网页驱动时，人不在电脑前，任务就停在那里 | 已修：增加由所有者在本机选择的权限档。默认“受保护”，行为不变；“完全访问”下，Agent 请求的权限由运行时立即批准（选“仅此一次允许”的那个选项），每次批准都留有标记为自动的记录；切到完全访问时正在等待的批准也一并放行。Agent 的提问和没有“允许”选项的请求仍然等人回答 |
| PF2 | 中 | 完全访问档下，以所有者身份连接的客户端仍然不能共享文件夹、放宽只读、读取凭据文件、设置引擎、回答 Agent | 已修：这些在完全访问档下对所有者身份放开（通过 `operations_call`，内嵌工作台里对应的按钮也恢复）。登录的成员身份不受影响 |
| PF3 | 中 | 权限档本身不能被连接进来的客户端打开，否则等于没有默认档 | 已修：`access.update` 只在本机可用，任何 MCP 路径都到不了；有用例。`AGENTS.md` 的对应规则补了这一条例外，并写明它不能成为默认、不能经 MCP 到达 |
| PF4 | 低 | 用户需要知道自己处在哪一档、风险是什么 | 已修：`devmate access`、VS Code 的 **Change Permission Profile**（打开前有模态确认）、Obsidian 的 **Permissions…**；体检会报告，公网地址没有登录时报警告；工作台标题显示 “Full access”；README 两种语言和 SECURITY 写明了含义 |
| PF5 | 设计 | 完全访问是否应该成为默认 | 不做：DevMate 上架在两个市场，默认 `auth.mode: none`。把“任何能访问地址的人不经询问就能读凭据、自动批准 Agent”设为所有人的默认是不负责任的；3.x 的默认也不是 `fullAccess` |


第四批提交并推送到 `develop` 之后，这些工作流第一次在 GitHub 上运行：Windows（含真实 VS Code 的多开测试）、macOS、真实 Godot 三个任务通过，macOS 是第一次在任何地方运行；两个 Ubuntu 任务失败在同一个用例上，暴露的是 BS11。修复之后的提交上，Windows、macOS、Ubuntu（Node 24 和 26）、真实 Godot 五个任务和汇总检查全部通过。发布流程从分支手动运行了一次（只验证、不发布），验证并构建通过，四个发布作业按预期跳过。发布作业本身（创建 Release、Azure 登录、市场发布、来源证明）要到第一次推送标签时才会真正运行。`npm run check` 检查了每个动作都固定到提交。

## 经核查无问题的部分

路径输入的遍历/绝对/UNC/设备名/备用数据流均被拒；联接点与符号链接在任意层级被拒；ripgrep 与 ssh 参数无注入；成员按 ID 越权全部被挡；仅本机操作从任何 MCP 路径都不可达；OAuth 的码、令牌、PKCE、刷新轮换实现正确；客户端元数据抓取的 SSRF 防护完整；安装包内无测试、源码映射、密钥或本机绝对路径；工作台无注入点；OpenAI 隧道启动参数与官方文档一致；`plugin.json` 格式真实有效；直接驱动用户本机的 `claude` 符合 Anthropic 条款。

## 未能验证

- 真实 ChatGPT、Claude.ai 的端到端连接和登录；真实 Cloudflare 隧道和 OpenAI 隧道。
- 任何真实模型轮次：全程没有向任何模型发送过提示，Agent 适配器只用 `--version`、`--help` 和协议结构核对过。
- Gemini 与 Grok CLI（本机未安装）；Codex 与 DevMate 的实际连接（只验证了它接受配置）。
- 真实 Obsidian 里的插件；VS Code 的远程会话（Remote-SSH/WSL/容器）。
- macOS：全量测试和候选包构建已在 GitHub 的 macOS 机器上通过，但没有人在 macOS 上实际用过。针对它的修复里，从 Dock 启动时的 PATH 补全和旧版 Git 的提示仍然只有按平台参数或样例输出写的测试。Linux 已在 Ubuntu 24.04（WSL 2）上实跑，但只有这一个发行版、这一种文件系统；原生安装、其他发行版、桌面环境里的 VS Code 和 Obsidian 没有试过。
- 真实的发布：CI 已在 GitHub 上全部通过，发布流程的“验证并构建”也跑通了；创建 Release、Azure 登录、发布到市场、生成来源证明这几步只在推送标签时运行，还没有发生过。
- 真实 Godot、Playwright 会话、逆向后端（LIEF、pefile、pyelftools、Rizin、Ghidra）。
- 发布工作流：重写后的流程没有实际运行过。市场发布依赖的 Azure 登录、Open VSX 和 npm 两个可选作业、构建来源证明都只按文档和 3.x 的用法写成。第一次发布建议先从分支手动运行一次（只验证、不发布），再推送标签。
- 第三轮的规则收紧对真实客户端的影响：ChatGPT 和 Claude 里的内嵌工作台在默认档下不能回答审批、不能添加项目，只在测试里确认过表现为按钮不可用并提示去本机操作。
- 完全访问档的自动批准只用模拟的适配器测过（Claude、Codex、ACP 三种选项格式）。真实的 Codex、Claude Code、Gemini、Grok 在一次真实任务里的表现没有验证，因为那需要发起真实的模型请求。
