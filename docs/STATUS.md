# DevMate 现状

这份文档只讲 DevMate 现在的状态：还没做的、只做了一部分的、没法验证的，以及实测的性能。已经完成的事情不记在这里，它们在代码、测试和[更新日志](../CHANGELOG.md)里。

## 还没做，或只做了一部分

### 连接

- 快速隧道的地址在每次启动后都会变，客户端要换成新地址。地址固定的通路里，OpenAI 隧道只需要所有者在 OpenAI Platform 上建一条隧道（给 ChatGPT 用）；其余几种（自己的中继、Cloudflare 命名隧道、HTTPS 代理、SSH）需要所有者自己的服务器或域名。
- 运行时自己发出的请求（对接 OpenAI 隧道、通路自检、OAuth 客户端信息获取、外部 MCP 服务器）走这台电脑的代理：`HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` 变量，Windows 上没有这些变量时用当前账户的系统代理（开关变化在一分钟内跟上）。还不支持的：代理脚本（PAC）、只有 SOCKS 的系统代理、macOS 和 Linux 桌面的系统代理设置；这几种情况请设置 `HTTPS_PROXY`，体检会指出。连接器子进程（`cloudflared`、`ssh`）和委派的 Agent 只继承环境变量里的代理，不继承 Windows 系统代理。经代理验证过的只有本机替身代理，没有经过真实的 Clash 或公司代理。Node.js 低于 24.14 时运行时照常启动，但它自己的请求不走代理，体检会指出并提示升级。代理工具用 TUN 加虚假地址（域名解析成 198.18.x.x）时，启用了登录（OAuth）的公网地址无法完成登录：登录要核对客户端的真实地址，这道校验不为这种模式放宽，报错里会说明改用系统代理模式或设置 `HTTPS_PROXY`。
- 内置的 OpenAI 隧道客户端不实现“集群纠正”这项可选能力（`wrong-cluster-v1`），也不启动 Cloudflare 托管伴随进程；它只实现文档规定的两种命令，其余种类会被跳过并在体检里指出。
- OpenAI 隧道可以和一条带公网地址的通路同时开（`devmate connect … --openai-tunnel <id>`，或者给现有的通路加上：`devmate connect beside --openai-tunnel <id>`），只在命令行里配置：VS Code 和 Obsidian 的向导里还没有这一项。在向导里改连接会保留已经配好的那条隧道，改成“仅本机”或“OpenAI 隧道”时除外。同时开的时候隧道一律由运行时自己对接，不能用 OpenAI 的 `tunnel-client` 程序。用真实账号试过的只有一种组合：2026 年 10 月，快速隧道加 OpenAI 隧道，两个账号的 ChatGPT 各走一条，进同一个运行时，用的是发布前的构建。其余只对 OpenAI 服务的替身验证过：从外面冒充隧道那一路会被拒，公网一侧要求登录时隧道一路不要求，和快速隧道同开时隧道一路仍然是事件流；中继加隧道、`connect beside` 只在测试里走过，没有对着真实的中继服务器试。
- 自己的中继（`devmate relay setup`）在命令行里配置；VS Code 和 Obsidian 的向导里还没有这一项。中继的服务器脚本支持有 `apt-get`、`dnf` 或 `apk` 的系统，或者已经装了 Caddy 的系统。
- 快速隧道是 Cloudflare 提供给测试和开发用的：不保证可用性，最多同时 200 个请求，不支持事件流。DevMate 经它只回普通 JSON，调用进行中不发进度消息。它适合试用，不适合当日常通路。
- 更换连接方式或地址后要重启运行时。只是保存了新凭据的话，重启连接器就够了（`connection.restart`）。
- 工作台里不能配置连接和登录，也没有一张“现在共享了什么”的清单。
- Obsidian 里只能设置快速隧道或仅本机。需要域名或凭据的通路要用命令行或 VS Code 配置。
- 浏览器端客户端的来源放行（`allowedOrigins`）只能改配置文件，向导和体检都不涉及。
- VS Code 的连接向导没有步骤计数，也不能返回上一步。
- 没有 ChatGPT 网页里逐步点击的图文步骤。

### 安全与权限

- 在 Windows 上，实例目录放在用户目录之外时，本机其他账户可能读到令牌和凭据。体检会警告，但不会代为设置访问控制。
- 经 ACP 接入的 Agent（Gemini、Grok）没有 MCP 隔离，会加载用户在该命令行里自己配置的 MCP 服务器。
- 委派给 Codex 的会话不带所有者在 Codex 里配置的 MCP 服务器。做法是按名字逐个关掉，并连同 Codex 的 apps（账号的连接器）和 plugins（插件，它们自带 MCP 服务器，`codex mcp list` 里看不到）一起关掉，所以委派的 Codex 会话里也没有插件带来的技能。启动后 DevMate 向 Codex 核对这个会话实际够得着哪些服务器，多出一个就不启动。要让委派的会话照所有者的 Codex 原样运行：`providers.configure {provider:"codex", settings:{inheritMcpServers:true}}`。在 4.0.5 上这套隔离对 Codex 0.161.0 不成立（线程收到的配置会整张表盖掉启动参数里的同名表，被关掉的服务器全都回来了），委派因此要么等满 30 秒超时、要么被判隔离失败；修正后在同一台电脑上实测：只有 DevMate 的通道连着，核对用时约 0.2 秒，会话 1.1 秒就绪。这个修正还没有发布。
- 读写其他进程内存的逆向工具随安装包一起分发。它们默认关闭，只有所有者在本机才能打开。
- 快速隧道没有登录。地址末尾每次启动新生成的密钥是唯一的凭据：客户端保存了地址就等于保存了密钥，拿到完整地址的人拥有所有者的权限。
- 受保护档不是沙箱：只要共享了一个可写项目，客户端就能运行命令，命令以所有者的系统账户执行。只有全部项目都是只读时，各项限制才是真正的边界。
- 派发先确认（`devmate delegation ask`，默认）拦的是经 DevMate 交给编码 Agent 的任务。有可写项目的客户端仍然可以用命令行工具直接运行 `codex`、`claude`，那同样花所有者的额度，这道确认拦不住。确认只能在电脑前回答：所有者不在电脑前、又没有事先设成 `allow` 时，从聊天客户端派发的任务会一直等着，不设超时（等的时候不启动进程、不占会话名额、不挡 Agent 的其它任务；同时在等的最多 20 个，再多的直接拒绝并说明所有者还有多少个没答；从 `allow` 改回 `ask` 时，已放行但还没开始的任务按先后回到等回答，到 20 个为止，多出来的直接结束并说明）；任务被撤回、Agent 被停止、所在工作流被完成、项目被移出共享、副本里的工作被采纳或丢弃，或运行时重启时，这个问题才结束。在等的任务不计入工作流的轮次，允许时才计。允许的那一刻任务开始不了（这个厂商的会话名额满了，默认 8 个；工作流被暂停或轮次用完了；项目被改成只读；上一个进程还没确认退出），回答会被拒绝并说明卡在哪里，问题原样留着，要等那件事过去后再点一次，或者拒绝；设成 `allow` 时这类任务继续等着并说明在等什么（对来问的客户端和工作台卡片都说），在有会话结束、工作流或项目被改动、会话名额被调高时自动再试并放行。“这个 Agent 之后的任务也允许”说的是它当时的那个会话，只到会话结束为止（停止、进程没了或没起来、运行时重启），空闲 30 分钟断开后要重新问。被拒绝（或被撤回、赶上运行时重启）而且从没启动过的 Agent 会被关闭，客户端要重新派一个，不能接着它派；为它建的工作副本一起删掉，删不掉的（文件夹还被别的程序占着）留在这个 Agent 名下，之后用 `agents.discard` 丢弃。问题里凡是别人起的名字（Agent、项目、模型、要接续的会话）都放在引号里、压成一行并截短，名字里自带的各种引号一律显示成撇号，客户端选的模型和会话会标明。完全访问档下，客户端可以回答 Agent 在任务里提的问题，这是客户端的文字进入正在运行的任务的第三条路，这道确认和 `off` 都不拦它，只是之后这一轮转交给别的 Agent 的内容会被问。仍是 4.0.5 的入口（比如没更新的 Obsidian 插件）在被这一版用过的实例上启动不了运行时，会说明涉及哪两个版本，但可以接入正在运行的运行时；这靠状态的格式编号做到，升了编号之后也回不到 4.0.5。旧入口被拒这一条实际试过，用的是一个状态代码与已发布的 4.0.5 逐字相同的构建（不是 4.0.5 的发布包本身）：它对被这一版用过的实例执行 `start` 被拒并说明原因，随后这一版的运行时在同一个目录上照常启动，项目都在。2026-10-12 另一个会话在一个独立实例的真实运行时上经本机 MCP 入口走过这套确认，没有启动任何 Agent：派发后立刻得到“要所有者先允许”、Agent 是 `unstarted`、问题里有模型和任务全文；客户端回答问题、改这个设置、`agents.steer`、`agents.resume` 都被拒；带等待的 `agents_result` 等满了时间才回来；所有者拒绝后任务以“所有者没有允许”结束、Agent 被关闭；`devmate delegation off` 结束在等的任务，之后连上的客户端看不到派发工具。“允许之后真的运行”没有走过。VS Code 和 Obsidian 只弹提醒并打开工作台，没有自己的“允许 / 拒绝”按钮；浏览器扩展的弹窗只显示有几件事在等，内容不送进浏览器；这个开关只在命令行里改，编辑器和工作台里还没有入口。Claude Code 的 `nativePeerMessaging`（默认关）打开后，Claude 的会话之间自己传话，不经过 DevMate，这道确认管不到。这套确认只用替身 Agent 验证过，没有用真实的 Codex 或 Claude Code 走过“先确认、再运行”。

### 运行时

- 事件日志只按保留天数清理，没有大小上限。
- 用过旧的游标重新连接事件流时，没有“中间有缺口”的提示。
- `/health` 不反映连接器正在反复重启。
- `operations.read` 对不带项目信息的历史结果不复查授权。
- `devmate mcp` 收到取消通知时只是转发，上游不会因此停止等待（最长 50 秒）。
- 能力调用（`capability_call`）没有统一的时长上限：浏览器导航最长 120 秒，Godot 的运行和测试最长 15 分钟，都超过客户端对单次工具调用的限制（Claude 240 秒，ChatGPT 据称约 1 分钟）。这类调用要用 `job.start` 作为作业启动，运行时不会自动改走作业。作业用 `job.read` 的 `waitMs` 等到结束（一次最多 50 秒）；输出在作业结束时才记入作业。命令作业运行期间已经打印的内容用 `process_read` 读，进程号在作业的 `processId` 里；能力作业运行期间没有中途输出。这两点只有自动化测试，没有经真实客户端走过。
- 同时连着两个浏览器（比如 Chrome 和 Edge）时，标签页、窗口、书签这些 id 不带“是哪个浏览器给的”。一个浏览器走掉之后，模型拿它给的旧 id 发来的新调用，会发给现在连着的那个浏览器，在那边对应的是另一个东西。已经在排队的调用不会这样改道。同一个浏览器重新连上（它的宿主进程换了一个）时，运行时认不出它是原来那个，排在旧连接上的改动类调用和带 id 的调用会被退回，由调用方重发。
- Windows 上标了“只读”的单个文件，文件工具不替换、不追加、不单独删除（`read_only_file`）。整个文件夹递归删除时，里面的只读文件会一起删掉，和其它文件一样进历史、可以取回：`.git` 里的对象文件就是只读的，拒绝会让带仓库的文件夹删不掉。
- Agent 通道只支持 2025 版握手。
- ACP 适配器按“模式”读取权限设置，没有按协议新的配置项方式实现。
- 保存的状态带格式编号，但还没有在格式变化时升级状态的机制。

### 模型一侧

- 工具清单按客户端分三份（实测，`tests/runtime-surfaces.test.mjs`）：GPT 面 34 项 33,574 字节，Claude 面 36 项 33,830 字节，通用面 37 项 36,144 字节；分面之前是一份 39 项 40,135 字节。只读的工具、能力三件套（`capability_list`、`capability_query`、`capability_call`）和撤回改动都在每一份清单里：曾经为了把清单压到 18 到 21 KB 而把它们挪到 `operations_query` / `operations_call` 后面，那是做差了（模型看不到就不用；只读工具不触发客户端的确认，改走命令行反而每次都要确认），已经改回。每个工具约 500 字节是协议要求的结构（输入模式、四个提示、状态文字）；还想更小只能靠压短描述，这一步没有做。
- 按客户端选工具面还没有用真实的 ChatGPT 或 Claude.ai 验证过：识别靠客户端自报的名字（`openai`、`chatgpt`、`codex`、`gpt` 归 GPT 面，`claude`、`anthropic` 归 Claude 面）、请求的 User-Agent，以及“经 OpenAI 隧道进来的就是 ChatGPT”。说 2025 协议的客户端只在握手时报一次名字，之后的请求只能靠 User-Agent 识别；认错时在 MCP 地址后加 `?tools=gpt|claude|generic` 指定；`devmate doctor` 会显示最近一个客户端自报的名字、User-Agent、分到的工具面和依据，真实的 ChatGPT 和 Claude.ai 报什么名字要到那里看。`devmate mcp`（标准输入输出）会把客户端的名字带给运行时。
- 审阅改动（`show_changes` / `workspace_changes`）只在 Git 仓库里可用：它对比的是上一次提交，“已审阅”按每个文件当前内容的哈希记。不是 Git 仓库的项目只能用改动历史（`workspace.history`）。它只给按文件的汇总，不带差异正文，也还没有可在界面里审阅的差异卡片。
- 命令和委派的默认等待是 30 秒，上限 50 秒，三个工具面一致（`exec_command` 的让出时间也是这两个数）。同类项目记录过“ChatGPT 宿主在约 12 秒处结束调用”，这一点没有用真实的 ChatGPT 实测过；如果实测属实，调用方可以用 `waitMs` 或 `yield_time_ms` 给更短的等待。
- `capability_list` 的 `summary:false` 会一次返回全部结构，体积很大。
- 在 Windows PowerShell 5.1 下，本地化的报错正文可能是乱码，并且会带出实例目录里的脚本路径。装了 PowerShell 7 就没有这个问题。
- MCP 引导请求（elicitation）用于审批、MCP Events、`.mcpb` 打包、MCP Registry 的 `server.json` 都没有做。
- 没有子目录脚本发现、标准输出与标准错误分开的进程输出、上下文包导出和命令行交互模式。
- 编码 Agent 的接入是代码，不是配置：新增一种 Agent 要改代码。
- 委派默认仍然直接在项目里改文件；要先看差异再应用，得在委派时加 `isolate:true`。隔离副本从最后一次提交开始，不含未提交的改动和被忽略的文件：依赖要在副本里重新安装才能跑测试，项目还不能预先配置“副本准备步骤”，委派结果里会说明副本缺什么。副本没有过期清理：运行时崩溃或 Agent 被丢下不管时，副本目录和 `devmate/copy-…` 分支会一直留着，直到应用、丢弃或把项目移出 DevMate；体检也还不列出现存的副本。工作台里还没有查看、应用和丢弃提案的界面。副本里 Agent 自己的权限请求照常要批准。
- 成组撤销（`workspace_restore` 的 `since`）覆盖 DevMate 自己的文件工具做的改动，以及从隔离副本应用进来的改动。不隔离的 Agent 和命令直接改的文件不在这份历史里，要靠 Git。
- 没有免安装的试用方式：命令行没有发布到 npm（发布流程里有这个作业，仓库没有配置 npm 凭据所以跳过），要从 Releases 下载安装包。
- 脱敏报告（`devmate doctor --report`）只能去掉它认得出的东西：凭据的常见写法、家目录和账户名、共享文件夹、公网主机名、IP 和邮箱。日志里其他形式的私人信息要靠发出去之前自己看一遍。VS Code 和 Obsidian 里还没有对应的命令。

### 界面

- 活动页的“Load earlier”按全局序号每次回退 300 条。在很忙的实例里，安静项目往前翻会很慢。
- 同一个概念的叫法没有完全统一：VS Code 的命令 ID 和工作台里仍然叫“project”，其他地方叫“共享的文件夹”。
- Obsidian 的笔记索引没有在元数据缓存就绪之后做一次全量刷新。
- Obsidian 插件把运行时源码以可读的纯文本内嵌在 `main.js` 里（约 10.6 MB），不是瘦客户端。
- Obsidian 写到实例目录里的运行时文件，换版本后旧的那一份不会清理。

### 测试

- 测试里还有靠短时限判断超时的用例。其中两个在繁忙的机器上失败过（准备数据的普通调用也被套上了 0.3 秒的时限），已经改成只给应当超时的调用设短时限；其余用例没有逐个排查。

## 有意保持的设计

这些是决定，不是遗漏。要改的话都是很小的改动。

- 权限档默认是“受保护”。“完全访问”由所有者在自己的电脑上打开。
- VS Code 默认把打开的受信任文件夹以读写方式共享，Obsidian 的共享询问默认选中“读写”。
- 编辑器窗口可以修改实例级的设置，因为它是所有者在本机的入口。
- 家目录不能作为项目共享，因为运行时自己的状态在里面。
- 有多个项目时，每次修改都要指明项目；不按会话记住项目。
- 覆盖文件的操作不标记为“破坏性”，因为被覆盖的版本可以恢复。
- 带正文的工具结果只有文本一种表示，所以工具不声明 `outputSchema`。
- 任务和消息是用户数据，不会自动清理。

## 没法验证的

- 扩展在这之后又改了一轮，还没有发布：点击、悬停、输入、按键、选择、滚动的每一步都在对话框监视之下，被对话框拦下的步骤事后不再继续，回答只说实际做了的事（`typed` 是真正打进去的字数）；截图不再等一个不回答的页面；按文字找元素先找包含这段字的最小一段文本；放在后面的标签页上找不到元素时先唤醒再找一次；标签页在 DevMate 第一次接触它之前就弹着对话框时，5 秒后说明原因和出路（在浏览器里关掉，或 `tabs.reload`），不再每次卡 30 秒；DevMate 自己的工作台页和扩展自己的页面，不经浏览器读、操作或导航走。这些是另一个会话在一次性配置的 Chrome 154 里用真实网页试的（18000 个元素的页面在内）；“工作台页被拒绝”还在所有者自己的 Chrome 上对正在运行的运行时试过。Edge、macOS、Linux 没有试。已知的限制：页面把密码写在 `value` 属性里时，用 CSS 选择器仍然问得出来（例如 `page.waitFor` 的选择器写成 `input[type=password][value^=a]`），选择器是调用方自己写的，拦不住，`page.inspect` 里这个值显示成 `(hidden)`；唤醒时页面弹了对话框，或唤醒中途页面在跳转，焦点模拟会留着，直到下一次成功的点击或调试器摘掉；浏览器正在显示的标签页的截图只问一次，浏览器不回答时靠运行时的 30 秒兜底，被放到后面过的标签页之后一直按“重问”的日程走；所有者自己把已登录的工作台标签页带到别的页面之后，客户端可以操作那个页面并让它后退回工作台，扩展在浏览器说出去向的那一刻摘掉调试器（实测 40 次抢跑没有一次得手），但同一两毫秒内已经发出的一次点击不能从原理上排除；扩展靠运行时告知的本机端口认出工作台页，运行时没有告知时只靠页面自己的标题。
- 全面检查之后改的一批，还没有发布。实测过的：ChatGPT 面的 `exec_command` 原先总给命令留一根没人关的标准输入，`rg <词>` 不带路径、`findstr`、`sort` 这类命令会一直等（在这台电脑上量过：8 秒后仍在跑、没有输出），现在默认不给，要用 `tty:true` 才给；查找和搜索不再让 ripgrep 排序、并且在输出够用时就结束它，在这个仓库连同依赖（约一万两千个文件）上搜一个常见词，从 10 到 17 秒降到 0.25 到 0.33 秒，查找的顺序与 ripgrep 自己排序的结果逐项相同（比过前 2000 项）；能力摘要的大小是 25.7 KB，其中浏览器的 52 个约 10 KB。只有自动化测试、没有在真实场景里走过的：更新之后命令行说“旧的运行时还在跑”（没有经一次真实的更新看过）；重启沿用原来的端口；中继服务器不应答时启动只等 5 秒（没有对一台真的不应答的服务器试过）；反向代理没传公网主机名时的说明；体检用 PowerShell 跑一条命令来发现“策略禁止运行脚本”（这台电脑没有这样的策略，只用替身验证了判断和措辞，真实的报错文字是本地化的，靠其中不随语言变的标识认）；编辑器找不到可用 Node 时带上各次尝试的原因；登录页说明验证码从哪里来。命中多到装不下时，搜索给出的是其中一部分，并且每次不一定是同一部分，结果里标着“被截断”；在这之前给出的也不是按路径最靠前的那些，而是输出的末尾一段。运行时的整理（过期日志和历史版本）改到启动 15 秒之后，之后每 6 小时一次；留了几千个历史版本时每次整理仍有零点几秒的停顿。文件夹不在的项目：在项目清单和给模型的说明里标出来，依据是上次看到的情况（后台每 30 秒最多看一次，不在每个请求上去问磁盘；一个调用碰到它不在时立刻标上，文件夹回来之后这个项目上第一次成功的调用立刻把标记去掉）；派给 Agent 的任务和各引擎的能力在动手之前就以同一句话拒绝，不再以“启动程序失败”的样子出现。那句话把“盘没接上”和“被移走、改名或删除”分开说：前一种接上就行、什么都不用删，后一种才是移除再重新共享，并说明移除会带走这个项目的工作流、任务和 Agent 记录。只有 Windows 的盘符整个不在时能认出是前一种；网络共享和别的系统上的挂载点分不出来，这时两种办法都说。Windows 上“输出够了就结束 ripgrep”曾把已经自己退出的进程一直记成“退出未确认”（每次这样的搜索留下一份几兆的内存和一次白等），已修，并有一个真的越过上限的测试连跑十轮；这个缺陷只在本地的提交里存在过，没有发布过。查找的顺序与 ripgrep 的排序相同，名字里有表情这类字符时也一样（比过）。2026-10-12 另一个会话用仓库源码在一个独立实例里起了真实的运行时（Windows 11，Node 24.21，Windows PowerShell 5.1），经本机 MCP 入口以 ChatGPT 的工具名走了一遍，没有启动任何任务：`exec_command` 跑 `rg -c <词>` 不带路径 0.3 秒结束并给出结果，`findstr` 同样；带 `tty:true` 的命令保持运行，`write_stdin` 能送字进去；不带 `tty` 的命令送字被拒并说明怎么重开。共享的文件夹被移走后，读文件、跑命令、派任务都以同一句话被拒，没有为它新建 Agent 或问题，体检有对应的一行，移回来后立刻可用。把一个约一万两千个文件的目录作为项目共享，搜一个常见词约 0.3 秒、按名字查找约 0.1 秒，交替六轮之后运行时名下没有子进程留着。这些没有经真实的 ChatGPT 走过。
- 用网页组件（shadow DOM）搭的页面，还没有发布：4.0.5 在这类页面上，元素结构里列得出按钮，按编号点却被当成“被别的元素挡住”（挡住它的是它自己所在的组件），按文字找不到元素，按文字等也等不到。改成：按文字找元素和按文字等待也看进组件里面，直接写在组件里的文字、插槽自带的后备文字、只把内容透传出去的包装（display: contents）里的文字都算；判断挡没挡住时，从元素自己所在的那棵树问起、一层层往外问，所以封闭组件里同一个组件的遮罩盖住按钮也看得见（上一版在封闭组件里看不见，点击落在遮罩上却回答点到了）。现在的限制：封闭的组件（不让页面脚本看里面的）里的元素按文字找不到、等不到，只能按元素结构里的编号操作；CSS 选择器只找页面自己的那棵树，组件里面的找不到；一个页面最多看进 2000 个组件；分散在几个元素里、外面又只有一个透传包装的词，等得到但按文字点不到（那个包装没有可点的位置）；同一个宿主下另一个插槽里的内容盖住按钮时不会被当成遮挡。页面里的框架（iframe）每一个都在元素结构里列出（没有名字的框架原先整个不出现），地址只为前 100 个去问，之后的不带地址；还没加载的框架按它要加载的地址显示，内容直接写在页面里的框架（srcdoc）没有地址；框架里面的内容仍然读不到也操作不了，可以用 `tabs.open` 把那个地址单独打开，站点不让单独打开的就没有办法。按文字等待超时不等于页面上没有：框架里的和封闭组件里的不看，超时的说明里这样写。这些是另一个会话在一次性配置的 Chrome 154 里用真实网页逐条试的（Windows）；Edge、macOS、Linux 没有试。
- Windows 上的注册经系统自带的管理服务（WMI 的 StdRegProv）读写当前用户的注册表，而不是 `reg.exe`：在打包应用里运行的程序（例如某些应用内置的终端）拿到的是 `HKCU\Software` 的一份私有副本，从那里用 `reg.exe` 写进去的注册浏览器永远看不到。这是在真机上撞到之后改的，改后的读取在同一台电脑上实测过（约 1 秒），写入和删除只用替身测过。注册只存在于那份私有副本里时，`devmate chrome` 报“未注册”并说明原因，重新执行 `devmate chrome install` 即可；卸载会把两处都清掉。
